Cuatro ideas que corrigen el modelo intuitivo

Son los malentendidos más habituales al empezar. Si te quedas con estas cuatro, el resto de esquemas encaja solo.

Construir no es ejecutar

La construcción ocurre una vez, antes de que llegue ningún usuario, y produce ficheros de texto. Una petición nunca dispara una compilación.

Node.js aparece dos veces

Primero como herramienta que construye y termina; después como servidor que ejecuta el backend y no se apaga. El JavaScript del front no lo ejecuta Node, sino el navegador.

Dos tipos de respuesta

nginx sirve ficheros iguales para todos (HTML, JS, CSS). El backend genera respuestas a medida, siempre en JSON. El HTML llega una sola vez, al cargar la app.

La frontera de confianza

Todo lo que hay en la zona Navegador está en manos del usuario: puede leer el bundle y fabricar peticiones con curl. Los secretos y las comprobaciones que importan viven en el backend.

Al margen

¿Y si el backend devolviera HTML?

Eso es SSR (Server-Side Rendering): en cada petición, Node ejecuta React en el servidor y devuelve el HTML ya dibujado; luego el navegador lo hidrata, es decir, React se engancha a ese HTML para hacerlo interactivo. Lo hacen frameworks como Next.js y es un módulo minor del subject.

Superfocus es una SPA (Single Page Application): el HTML llega una vez y después solo viaja JSON. Incluso con SSR no se recompila nada por petición: se ejecuta código ya construido.

Prueba tú mismo · 10 min

Construye el front fuera de Docker y mira qué sale

En srcs/apps/web, con Node 24 instalado con nvm:

npm ci                      # instala exactamente lo del lockfile
npm run build               # tsc -b && vite build
ls -la dist dist/assets     # lo que se publica
cat dist/index.html         # mira a qué ficheros apunta ahora
grep -o '.\{60\}LOGIN.\{60\}' dist/assets/*.js   # tu JSX, ya convertido
  1. Compara el index.html de la raíz con el de dist/. ¿Qué línea ha desaparecido y cuáles han aparecido?
  2. Cambia el texto LOGIN, vuelve a construir y compara el nombre del .js. ¿Por qué ha cambiado? ¿Y el del .css?
  3. Añade a LoginScreen.tsx una variable con un tipo incorrecto (const n: number = "hola") y construye. ¿Qué herramienta falla? ¿Llega a ejecutarse Vite?
  4. Busca en el .js generado alguna anotación de tipo de TypeScript. ¿Por qué no encuentras ninguna?
Soluciones

1. Desaparece <script type="module" src="/src/main.tsx">, que apuntaba al código fuente. Aparecen un <script> que apunta a /assets/index-<hash>.js y un <link rel="stylesheet"> a /assets/index-<hash>.css.

2. El hash se calcula a partir del contenido: al cambiar el código cambia el .js y, con él, su nombre. El .css no cambia, porque no has tocado ninguna clase.

3. Falla tsc -b con un error de tipos y termina con un código distinto de 0; el && impide que se ejecute Vite y no se genera un dist/ nuevo.

4. Porque los tipos se borran al transformar el código. En ejecución no existen: por eso el backend tiene que validar los datos que recibe aunque estén «tipados».

SeguridadEsto se ejecuta en tu máquina: npm ci descarga y ejecuta código de terceros con tus permisos. Hazlo solo en el repo del equipo, con el lockfile revisado, y nunca con sudo.

Sigue el recorrido en una web real

Cuando el backend esté listo podréis hacerlo con Superfocus. Mientras tanto, cualquier web con login sirve para ver las mismas piezas.

  1. Abre una ventana de incógnito, DevTools (F12) y la pestaña Network. Marca Preserve log para que no se borre al cambiar de página.
  2. Carga la web y ordena por la columna Waterfall. Localiza la petición del documento, las del .js y el .css, y las primeras de tipo Fetch/XHR. ¿Cuáles empiezan antes de que termine la anterior?
  3. Inicia sesión. En la petición de login, busca en Response Headers la cabecera Set-Cookie y anota sus atributos.
  4. Ve a Application → Cookies. Comprueba si la cookie tiene marcada la columna HttpOnly. En la consola, escribe document.cookie: ¿aparece?
  5. Recarga la página. En la columna Size, ¿qué ficheros vienen de (memory cache) o (disk cache), y cuáles devuelven 304?
SeguridadNo copies tus cookies de sesión de webs reales en ningún sitio: quien tenga esa cookie es tú para ese servidor hasta que caduque.

Cuatro preguntas antes de seguir

Visitas https://localhost/perfil. ¿Por qué nginx responde 200 y no 404, si no existe ningún fichero perfil?

Por try_files $uri $uri/ /index.html: si el fichero no existe, nginx devuelve index.html. Las rutas como /perfil las resuelve React en el navegador, no nginx.

¿Por qué React tiene que preguntar /api/users/me en lugar de mirar si existe la cookie?

Porque la cookie es HttpOnly y el JavaScript de la página no puede leerla. Y aunque pudiera, solo el servidor sabe si esa sesión sigue siendo válida (puede haber caducado o haberse cerrado desde otro sitio).

Tras el login, React cambia de /login a /perfil. ¿Cuántas peticiones a nginx genera ese cambio de pantalla?

Ninguna para el HTML: el router cambia la URL con la History API y pinta la nueva pantalla con el JavaScript que ya tiene. Solo hay una petición, la de los datos: GET /api/users/me.

Un atacante consigue ejecutar JavaScript en vuestra página (XSS). ¿Puede robar la cookie de sesión? ¿Puede hacer daño igualmente?

No puede leerla, gracias a HttpOnly. Pero sí puede hacer peticiones a /api/... desde la propia página, y el navegador les añadirá la cookie. HttpOnly limita el daño, no lo elimina: evitar el XSS sigue siendo imprescindible.

Cuatro preguntas antes de seguir

Con curl y tu propia cookie envías el POST con "userId": 5 en el cuerpo, para apuntarle la sesión a otro usuario. ¿Qué capa lo detiene?

El pipe: userId no está en el DTO y el pipe rechaza los campos de más con un 400. Y aunque no los rechazara, el controller no lo usaría: el usuario sale siempre de la sesión que comprobó el guard.

El backend recibe "durationMin": 25. ¿Qué puede comprobar y qué no?

Puede comprobar que es un entero dentro de un rango posible (el DTO) y rechazar el resto. No puede comprobar que sea cierto: el tiempo lo ha medido el navegador. Es una decisión del equipo, que confía en el front para este dato.

El service guarda la sesión y suma la XP del usuario. ¿Qué pasa si la segunda consulta falla y no hay transacción?

Quedaría guardada una sesión sin su XP, y los datos dejarían de cuadrar entre sí. Con una transacción, si falla cualquiera de las dos, se deshacen ambas.

Tras la respuesta, ¿descarga el navegador algún HTML? ¿Se vuelve a pintar la página entera?

No a las dos. Llega JSON, React actualiza su estado, compara lo que debería verse con lo que había y cambia solo los nodos del DOM afectados: la barra de XP, el número de nivel y el temporizador.

⓪ Repaso · para quien hizo ft_irc o webserv hace tiempo

Lo que ya sabes y lo que cambia

ft_irc y webserv eran servidores TCP que hablaban un protocolo de texto. HTTP es exactamente eso. Lo que cambia no es la red, sino tres cosas de encima: el formato de los mensajes, quién puede hablar y cuándo, y dónde se guarda quién eres.

Lo que te costó en ft_irc

TCP entrega bytes, no mensajes

Un recv() puede devolver medio comando o tres comandos juntos. Por eso en ft_irc guardabas un búfer por cliente y cortabas por \r\n. A eso se le llama delimitar los mensajes (framing), y cada protocolo lo resuelve a su manera.

HTTP lo resuelve en dos tiempos: las cabeceras terminan en una línea vacía (\r\n\r\n), y el tamaño del cuerpo lo dice la cabecera Content-Length (o el cuerpo llega troceado con Transfer-Encoding: chunked).

Lo que hiciste en webserv

Ese programa ahora es nginx

Leer la línea de petición, leer cabeceras hasta la línea vacía, leer el cuerpo según Content-Length, decidir por la ruta si se sirve un fichero o se pasa a otro programa, y escribir la respuesta. Eso es lo que hace nginx con el front.

El CGI de webserv es la idea del reverse proxy: nginx no ejecuta la lógica de /api/, se la pasa al backend. En el backend, el módulo http de Node hace el mismo análisis y NestJS os entrega la petición ya convertida en un objeto.

SeguridadIgual que el client_max_body_size de webserv, nginx y NestJS deben limitar el tamaño del cuerpo. Sin límite, cualquiera puede agotar la memoria del servidor enviando un cuerpo enorme.

Anatomía de un mensaje HTTP

Una petición de Superfocus (guardar un pomodoro terminado) y su respuesta, tal como viajan dentro del canal TLS. El cuerpo largo se parte en pantalla, pero viaja en una sola línea. ␍␊ marca cada \r\n. Pasa el ratón o enfoca cada parte de la leyenda para resaltarla.

Petición · navegador → servidor

Host: localhost␍␊
Cookie: sid=9f2c41e07b␍␊
Content-Type: application/json␍␊
Content-Length: 34␍␊
␍␊
{"durationMin":25,"tag":"estudio"}
Respuesta · servidor → navegador
HTTP/1.1 201 Created␍␊

Content-Length: 82␍␊
␍␊
{"id":118,"durationMin":25,"tag":"estudio","xpGained":25,"totalXp":1340,"level":7}
  1. Método. Qué quieres hacer: GET leer, POST crear, PUT/PATCH modificar, DELETE borrar. Equivale al comando de IRC (JOIN, PRIVMSG).
  2. Ruta. Sobre qué recurso. Método + ruta forman un endpoint. nginx la usa para decidir si es un fichero o algo para el backend.
  3. Versión. Nuestro nginx habla HTTP/1.1. HTTP/2 y HTTP/3 transportan lo mismo (método, ruta, cabeceras, cuerpo) en formato binario: el modelo no cambia.
  4. Cabeceras. Pares Nombre: valor, una por línea. Dicen a quién va (Host), quién eres (Cookie), en qué formato va el cuerpo (Content-Type) y cuánto mide (Content-Length, en bytes).
  5. Línea vacía. Separa cabeceras y cuerpo. Es el delimitador que buscabas en webserv.
  6. Cuerpo. Los datos, aquí en JSON. Exactamente Content-Length bytes. Un GET normalmente no lleva cuerpo.
  7. Código de estado. El resultado en un número: 2xx bien, 3xx ve a otro sitio, 4xx el cliente hizo algo mal (400 datos inválidos, 401 no has iniciado sesión, 403 no tienes permiso, 404 no existe), 5xx falló el servidor.
El mismo gesto en IRC
:pedro!pedro@host PRIVMSG #42 :25 minutos de estudio␍␊

Una sola línea de 512 bytes como máximo, sin cabeceras ni cuerpo separados, y sin respuesta obligatoria. En HTTP cada petición recibe exactamente una respuesta.

SeguridadTodo lo que hay en la petición lo escribe el cliente, y el cliente puede ser curl en lugar de nuestro front. Cabeceras, ruta, cuerpo y Content-Length pueden ser mentira. El backend no se fía de nada que no compruebe: por ejemplo, nunca acepta un userId en el cuerpo, lo obtiene de la sesión.

Cuatro preguntas antes de seguir

Un recv() te devuelve 1.000 bytes de una petición HTTP. ¿Cómo sabes si ya la tienes entera?

Buscas la línea vacía (\r\n\r\n): ahí terminan las cabeceras. Lees Content-Length y esperas hasta tener ese número de bytes de cuerpo después de la línea vacía. Si no hay cuerpo ni Content-Length, la petición termina en la línea vacía.

En ft_irc, tras NICK y USER no repetías tu nick en cada mensaje. ¿Por qué en HTTP hay que mandar la cookie en cada petición?

Porque HTTP no tiene estado: cada petición se interpreta sola, aunque viaje por una conexión ya abierta (y el navegador puede abrir varias conexiones o cerrarlas cuando quiera). La cookie es lo que permite al backend saber quién eres en cada una.

Un amigo empieza una sesión de concentración. ¿Puede el servidor avisarte por HTTP?

No. En HTTP el servidor solo responde a peticiones. El front tendría que preguntar cada pocos segundos (polling) o abrir un WebSocket, que permite al servidor enviar cuando quiera, como en ft_irc.

¿Qué código de estado esperas si envías el POST de arriba sin la cookie? ¿Y si la envías pero con "durationMin": -5?

Sin cookie: 401 Unauthorized (no sabemos quién eres). Con datos inválidos: 400 Bad Request. Ambos son 4xx porque el error está en la petición, no en el servidor.
